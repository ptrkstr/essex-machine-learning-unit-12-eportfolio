Gradient Descent and the Cost Function¶

Unit 8 e-Portfolio activity for Machine Learning (PCOM7E). The brief sets the Mayo (2017) reading, then asks that the supplied gradient descent tutorial be run with the iteration count and the learning rate changed so that the effect on cost can be observed.

The supplied notebook fits a straight line to five points by gradient descent. Its own header states the aim as reaching the minimum cost in the fewest iterations, and warns that a low iteration count combined with a high learning rate may overshoot the global minimum. Both claims are treated here as propositions to be tested rather than repeated, because the dataset makes that possible: the five points lie exactly on y = 2x + 3, so the true optimum is known in advance and every run can be measured against it rather than only against its own starting cost.

The cost function and its gradient¶

The cost is the mean squared error between the predicted and the actual values. Squaring serves two purposes: it prevents positive and negative deviations from cancelling, and it penalises a large deviation disproportionately more than a small one.

The two partial derivatives give the direction of steepest increase in cost with respect to the slope and the intercept, so subtracting them moves the parameters downhill. The learning rate scales how far each of those steps travels. Mayo (2017) frames the objective as locating the point at which the rate of change falls to zero, and notes that the steepness measured where the parameters currently sit is what reveals whether the adjustment is heading the right way.

In [3]:
def computeCost(slopeValue, interceptValue, xValues, yValues):
    predicted = slopeValue * xValues + interceptValue
    return nplib.mean((yValues - predicted) ** 2)


def descendGradient(xValues, yValues, iterationCount, learningRate):
    slopeValue = 0.0
    interceptValue = 0.0
    sampleCount = len(xValues)
    costTrace = []

    for stepIndex in range(iterationCount):
        predicted = slopeValue * xValues + interceptValue
        residuals = yValues - predicted

        currentCost = nplib.mean(residuals ** 2)
        costTrace.append(currentCost)

        slopeGradient = -(2 / sampleCount) * nplib.sum(xValues * residuals)
        interceptGradient = -(2 / sampleCount) * nplib.sum(residuals)

        slopeValue -= learningRate * slopeGradient
        interceptValue -= learningRate * interceptGradient

    return slopeValue, interceptValue, costTrace

What the iteration sweep shows¶

Cost decreases monotonically with more iterations, but the returns diminish sharply and the intercept is what holds the fit back. The slope reaches its true value of 2 quickly, whereas the intercept approaches 3 far more slowly.

The reason is visible in the two gradient expressions. The slope gradient is multiplied by the feature values, which run from 1 to 5, while the intercept gradient is not. The slope therefore receives a systematically larger update from the same learning rate, so a single shared rate cannot suit both parameters at once. On a real dataset this is the standard argument for standardising features before applying gradient descent, since unscaled features produce exactly this imbalance.

What divergence looks like¶

The warning is confirmed, though the failure is more abrupt than the phrase "missing the minimum" suggests. Rather than settling at a slightly worse solution, the cost grows without bound: each step overshoots the minimum and lands further up the opposite side of the curve than it started, so the next gradient is larger still and the process compounds.

The threshold is also narrower than the supplied default implies. The tutorial ships with a rate of 0.08, which converges to a cost of 0.004, yet 0.085 already ends at a cost of roughly 809, far worse than the starting cost of 89. By 0.09 the run has diverged past any usable value entirely. The default therefore sits immediately below the boundary, with no margin: a single increment of 0.005 is enough to move from the best result in the sweep to a failed one.

This is worth separating from the local-minimum problem. Mayo (2017) observes that the ordinary form of the algorithm can become trapped short of the best solution, precisely because it consults the whole training set before making any single correction, which leaves it little freedom to explore elsewhere on the surface. The failure above is not that: mean squared error on a linear model is convex, with a single global minimum and no local ones to be trapped in. The run fails purely because the step length is too large for the curvature, which makes the point that a converging optimiser needs both the right objective and a step size matched to it.

The trade-off the grid exposes¶

The supplied header states the goal as minimum cost in minimum iterations, and the grid shows why those two aims pull against each other.

Reading down a column, a larger rate reaches a lower cost for a fixed budget of iterations, right up to the point where it destabilises. Reading across a row, a small rate can still reach a low cost, but only by spending far more iterations to get there. The cheapest reliable settings sit on a diagonal rather than at either extreme, and the fastest setting is adjacent to the one that fails outright, which is precisely what makes tuning the learning rate awkward in practice.

Mayo (2017) raises the question of how far to move in a direction and how the learning rate should be determined, then sets it aside as a separate matter. The grid above is a small empirical illustration of why it warrants that separate treatment.

The logarithmic vertical axis is necessary because the four runs differ by several orders of magnitude. It also makes the shape of each descent legible: a straight line on this scale indicates cost falling by a constant proportion per iteration, and the flattening at the right of the faster runs marks the point where further iterations buy very little.

Findings¶

Running the tutorial across both variations supports four observations, each traceable to a printed figure above.

The iteration count and the learning rate are not independent controls. A low rate can reach a good fit given enough iterations, and a higher rate reaches it sooner, so the sensible configuration is a combination rather than a best value for either in isolation.

Raising the learning rate improves matters only until it does not, and the transition is abrupt rather than gradual. The tutorial's default of 0.08 gives the lowest cost of any rate tested at 100 iterations, but 0.085 already ends worse than it started and 0.09 diverges outright. The best setting available therefore sits directly beside a failing one, with no gradual warning in between.

Divergence here is an overshoot, not a local minimum. Mean squared error on a linear model is convex, so the failure is caused by the step length relative to the curvature rather than by the shape of the objective, which distinguishes it from the entrapment risk Mayo (2017) describes.

The slope and the intercept converge at different rates because the slope gradient is scaled by the feature values while the intercept gradient is not. One shared learning rate therefore serves the two parameters unequally, which is the practical argument for standardising features before applying gradient descent to a real dataset.
